## What I did and why

The last iteration killed the DRAM term (`off_chip_bytes` 3.21M → 328K, energy 95.7 → 32.2 µJ). That moved the bottleneck onto the array itself — `exe_active = 0.90`, compute bound. And the counters are unambiguous about where the waste is: `macs_issued = 8,388,608` against `macs_useful = 524,288`. **93.75% of every multiply the mesh performs has a zero streaming operand**, and all of them are being computed densely, because the T-A datapath has been sitting in `PE.scala` with `SparseCraftRTL.gateEnable = false` for both measured iterations. That is the single largest untouched lever on the board.

Two coupled parts, one mechanism:

1. **Turned the gate on** — `gate_enable: 0 -> 1` in the marker header, which is what regenerates `SparseCraftRTL.gateEnable`. I did *not* hand-edit `SparseCraftRTL.scala`; it is loop-generated and outside my writable set.

2. **Fixed the isolation, not just the detection.** The stock gate freezes `mac_unit.io.in_a` only. But the MAC is a multiplier *and* an adder, and in WS the adder's other input is `io.in_b` — the partial sum flowing down the column, outputType-wide, toggling every single cycle regardless of the gate. That is precisely the failure mode the brief names as "`MAC_GATED_TOTAL` high but energy flat: detecting but not isolating." I added `sc_mac_c`, a held psum selected on a gated cycle, so both adder inputs are static (the product is already static — `sc_mac_a` is held and the WS weight `c1`/`c2` is stationary). The whole MAC datapath goes quiescent instead of half of it.

Bit-exactness argument is unchanged and is the same one the existing code relies on: whenever `sc_gate` is high, `mac_unit.io.out_d` is **discarded** by the output mux in favour of `b` itself, so whatever the MAC computes from held inputs is never observed. `c + 0·w ≡ c`. I deliberately kept the gate condition at `a_is_zero && in_valid` rather than widening it to `!valid` — that would change `out_b` on invalid cycles from garbage-A to garbage-B, which I can't prove never latches, and a correctness failure is scored worse than a regression. The OS branches are left byte-for-byte stock. With `gateEnable=false` the Scala `if` builds no hardware at all, so the disabled netlist is still identical to vanilla by construction.

I did not add a weight-side comparator: in WS for `Y = A·X` the stationary operand is dense `X`, so a second comparator would buy ~nothing and spend Fmax on the MAC critical path.
