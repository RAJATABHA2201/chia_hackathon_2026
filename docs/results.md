# Results

Every number here is regenerated by `python scripts/summarize_runs.py` from the
records in [`../results/`](../results/). This page says what was measured, what
was modelled, what the agent changed, and what to be careful about.

## Setup

| | |
|---|---|
| workload | `dnn512`: `Y = A * X`, `A` a 512x512 INT8 sparse matrix derived from a SuiteSparse pattern and stored as 16x16 blocks (512 of 1,024 blocks nonzero; 6.2% density inside the nonzero blocks), `X` dense 512x64 |
| baseline | stock Gemmini, 16x16 weight-stationary array, 256 KB scratchpad, 64 KB accumulator, running the **block-sparse** SpMM kernel (`kernels/spmm.c`, all-zero blocks skipped in software). Measured by the harness as iteration 1 of each run. |
| agent | Claude Code (`claude-opus-5`), sealed to the harness's MCP tools; effort `high` for V2 (proposer and repairer), `xhigh` for V1 |
| budget | 15 iterations per run, iteration 1 = the unmutated baseline |

**Measured:** cycles (Verilator RTL simulation of the full SoC), off-chip bytes
(Gemmini DMA counters), functional equivalence (every output checked against a
golden `A * X` computed on the host core), logic area (yosys, NanGate45).

**Modelled:** SRAM macro area (from capacity, fakeram45 datasheet figures, added
to the measured logic area) and **energy** (`src/t1_model.py`, from the measured
counters: 0.30 pJ per issued MAC, 1.2 pJ per SRAM byte scaled by
`sqrt(max(SRAM, 32 KB) / 256 KB)`, 22 pJ per off-chip byte, less T-A-gated MACs
and T-B-skipped rows). OpenSTA timing and power are recorded but unusable:
yosys maps without buffering, so every design shows a meaningless ~0.2 MHz, and
the clock is held at the 2.0 ns target for every design.

|---|---|---|---|
| cycles | 106,650 | 50,862 | **2.10x fewer** |
| off-chip bytes | 3,211,264 | 327,680 | **9.8x less** |
| area | 4.0350 mm² | 3.1152 mm² | **22.8% smaller** |
| energy (modelled) | 95.67 µJ | 17.04 µJ | **5.61x less** |
| perf/W (modelled) | 10.96 GOPS/W | 61.5 GOPS/W | 5.6x |
| equivalence mismatches | 0 | 0 | |

Configuration: X held resident in the scratchpad (software schedule), T-A
zero-gated MACs and T-B zero-row skipping in agent-written Chisel, scratchpad
256 -> 64 KB, accumulator 64 -> 32 KB.

## What the agent changed, iteration by iteration (V2)

| it | layer | change | outcome |
|---|---|---|---|
| 1 | | baseline | |
| 2 | **software** | `x_resident` on: all of X held in the scratchpad (`-DSPMM_XRES`) | 1.34x cycles, 9.8x less off-chip, 3x energy, zero area |
| 3 | RTL (`PE.scala`) | T-A: zero-gated MAC | energy -7%, area +1.7% |
| 4 | RTL (`SparseCraftSparsity.scala`) | T-B: zero-row skipping | energy -17.5%, area +4.2% |
| 5 | config | 32x32 array | equivalence failed; the repairer proved it cannot work with 16x16-blocked data |
| 6-7 | config | the same 32x32 design | duplicates; see "The resume" below |
| 8 | memory | scratchpad 256 -> 128 KB | cycles -36%, area -17% |
| 9 | memory | scratchpad 128 -> 64 KB | area -10.5%, energy -12% |
| 10-11 | RTL (ZBU rewrite) | T-B granule 16 -> 8 -> 4 | area +3.6%, **no real energy change** (see corrections) |
| 12 | **software** | `b_blocks` 0 -> 4 | no effect: `0` (auto) already resolves to 4 |
| 13 | config | `has_normalizations` off | rejected by T0 (a rule inherited from an attention workload) |
| 14 | RTL | T-B granule 4 -> 2 | rejected by T0: bitmap over budget at any scratchpad size |
| 15 | memory | accumulator 64 -> 32 KB | the final design |

Loop behaviour: 10 admitted (including the baseline), 1 equivalence failure, 2
duplicates, 2 legality rejections, 0 infrastructure failures. Three repairs, all
correctly `NOT_ACTIONABLE`, so no rebuild was spent on a guess. The proposer's
per-objective predictions were right 30 of 36 times. Mean 21.9 min per
iteration, with synthesis overlapped with simulation.

## V1 and V2 compared

Both runs start from the identical baseline. Energy is re-scored with the
current model for both (V1's records used an earlier model that gave no credit
for SRAM below 256 KB or for T-B).

| | V1 best (it 15) | V1 (it 14) | V2 best (it 15) |
|---|---|---|---|
| cycles | 51,001 (2.09x) | 50,780 (2.10x) | 50,862 (2.10x) |
| area | **2.7703 mm² (-31.3%)** | 2.8729 (-28.8%) | 3.1152 (-22.8%) |
| energy | 18.86 µJ (5.07x) | 19.93 (4.80x) | **17.04 µJ (5.61x)** |
| sparsity | T-A | T-A | T-A + T-B |

Neither loop's best design dominates the other: V1 found the smaller design,
V2 the lower-energy one, and all three points lie on one combined Pareto front.
V1-14 and V2-15 have the same memory sizes, which isolates T-B: about 8% more
area for about 15% less energy. The two searches were shaped by their energy
models: V1's gave nothing for shrinking memory or for T-B, so area was the only
axis that moved; V2's rewards both.

What V2 adds as a loop: iterative repair with a debugging playbook, T-B made
measurable, bottleneck-driven strategy selection, prediction feedback, resume,
and overlapped synthesis (21.9 vs 40 min per iteration).

## Corrections and caveats

- **T-B granule credit (fixed).** The loop credited iterations 10-11's finer
  granules with energy the hardware cannot deliver: the ZBU interface skips
  whole rows only. Re-scored, the final design is 17.04 µJ (5.61x), not the
  14.73 µJ (6.50x) the run recorded. See [v1-to-v2.md §2.9](v1-to-v2.md).
- **The resume.** After iteration 7 the run was stopped and resumed with
  `--resume`: failed designs were not visible in the proposer's history, so it
  had re-proposed the failed 32x32 design twice. The fix and the resume are in
  [v1-to-v2.md §2.8](v1-to-v2.md); `results/v2-final15/resume.json` records the
  point, and every past admission was replayed and matched before continuing.
- **Thread count.** A first launch at 30 Verilator threads simulated the
  baseline in 28.4 min against 19.8-22.0 min at 16, and was stopped after one
  iteration (`results/v2-final15-t30-aborted`).
- **Unexplained: iteration 8.** Halving the scratchpad cut cycles by 36%
  (79,433 -> 50,862), and V1 saw the identical jump from the same move. The
  agent predicted no cycle change. Equivalence passed, so the result is
  correct; the mechanism is not yet understood.
- **Not measured: a dense baseline on `dnn512`.** The block-sparse kernel is
  already in the baseline, so the improvements above are on top of it. Its own
  contribution was measured on other workloads (7.5x fewer cycles on `jag512`,
  1.86x on `dnn128`), not on `dnn512`.
